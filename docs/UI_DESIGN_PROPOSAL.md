# 微信 AI 记忆库 · UI 设计方案

> 版本 v1 ｜ 面向对象：产品与开发 ｜ 状态：待评审

---

## 一、设计目标

把工具从"一堆控件的集合"变成**一条清晰的作业流水线**：选范围 → 看预览 → 导出。用户在任何时刻都应能回答三个问题：

1. 我现在在做什么？
2. 还要多久？
3. 出问题时我损失了什么？

---

## 二、现状诊断

以下问题均来自本项目实测记录，不是主观感受。

| # | 问题 | 依据 | 影响 |
|---|---|---|---|
| 1 | **存在两套并行界面**（经典窗口 + 玻璃仪表盘），功能与配置不一致 | 代码中存在 `MainWindow` 与 `GlassDashboardWindow` 两套窗口 | 用户困惑；配置分裂（一套记设置、一套不记） |
| 2 | **长任务无时间预期** | 实测 2,439 条 ≈ 4.5 分钟；全量 43,347 条 ≈ 43 分钟、1.6 GB | 用户以为程序卡死，中途强杀 |
| 3 | **进度不可取消** | 进度条只有页数，无取消入口 | 选错范围只能等待或强杀 |
| 4 | **PDF 不可搜索** | 实测 PDF 为纯图片、无文本层、文本算子为 0 | 用户拿到 183 MB 却搜不到任何内容 |
| 5 | **媒体被微信清理后无提示** | `msg/attach` 最早文件 2025-07-20，而用户查看的是 2025-05-04 | 显示 `[图片]` 被误认为程序缺陷 |
| 6 | **高风险操作缺少前置说明** | 「连接微信」会重启微信并可能要求扫码 | 用户不敢点，或点了被吓到 |
| 7 | **完成态无产物反馈** | 导出结束后仅弹窗一行路径 | 用户找不到文件、不知道生成了几个 |

## 三、设计原则

1. **任务优先**：界面按"用户要完成的事"组织，而不是按"程序有哪些模块"。
2. **状态可见**：任何超过 3 秒的操作，都必须有进度、剩余时间与取消。
3. **不惊吓**：高风险操作（重启微信）先解释后果，再执行。
4. **记忆用户**：会话、范围、输出路径、勾选项、窗口尺寸全部持久化。
5. **一处真相**：只保留一套界面，删除并行实现。
6. **可预期**：遵循 Windows 桌面习惯——系统标题栏、标准快捷键、右键菜单、拖放。

## 四、信息架构

单一主窗口，三段式 + 上下两条状态带：

```
┌─────────────────────────────────────────────────────────┐
│ 顶部状态带  应用名 · 本地处理标识 · 连接状态 + 数据量      │
├──────────────┬───────────────────────┬──────────────────┤
│ ① 来源与范围  │ ④ 记忆预览            │ ⑤ 导出内容       │
│ ② 会话        │   搜索框              │ ⑥ 输出位置       │
│ ③ 时间范围    │   消息流              │ ⑦ 导出预估       │
│   关键词      │   （图片/语音/占位）   │ ⑧ 执行按钮       │
│   统计三块    │                       │                  │
├──────────────┴───────────────────────┴──────────────────┤
│ 底部状态带  状态文案 · 进度条 · 剩余时间 · 取消            │
└─────────────────────────────────────────────────────────┘
```

**为什么是左-中-右，而不是标签页：**
用户的实际动作是**来回对照**的——改一下日期，看预览变没变；勾上 Markdown，看体积涨多少。左右并置让这种对照零成本，标签页则要求反复切换。

**为什么导出独立成右栏：**
导出是本程序唯一的产出动作，也是唯一耗时的动作。它需要常驻可见（含预估），而不是藏在某个菜单里。

## 五、关键流程设计

### 5.1 连接微信（高风险）

现状：点一下弹一个确认框就开始，用户不知道接下来会发生什么。

建议改为**三阶段显式流程**：

1. **准备面板**（不执行任何操作）
   - 说明：将重启微信一次、可能要求扫码确认、**原始数据库不会被修改**
   - 说明：预计耗时
   - 主按钮：「开始连接」
2. **执行中**
   - 分步进度：查找微信进程 → 提取数据库密钥 → 读取会话列表
   - 可取消
3. **结果**
   - 成功：显示账号与消息总数，自动进入预览
   - 失败：给出具体原因 + 「重试」

### 5.2 导出（核心）

四步反馈模型见附图：

| 阶段 | 界面反馈 | 相对现状 |
|---|---|---|
| 设定范围 | 左栏统一承载 | 收拢分散控件 |
| 实时预估 | 改范围即刷新页数/耗时/体积 | **新增** |
| 导出中 | 进度 + 剩余时间 + 取消 | **新增**剩余时间与取消 |
| 完成 | 产物清单 + 打开目录 | **新增** |

**关键约定**：任何阶段失败都保留已完成产物，重试不必从头开始。

### 5.3 媒体缺失（被动发现问题）

预览中遇到原图已被微信清理的消息时：

- 不以普通气泡呈现，改用**警告色描边**并写明「原图已被微信清理 · 无法导出」
- 顶部状态带汇总提示：「本范围内 43 张图片已无法获取」
- 首次出现时给出一次性说明：**微信会定期清理旧媒体，想要完整归档需在过期前导出**

这比让用户自己发现 `[图片]` 占位符要好得多。

## 六、组件与状态规范

每个可交互元素必须定义完整状态，避免"点了没反应"的观感。

| 组件 | 默认 | 悬停 | 按下 | 禁用 | 焦点 |
|---|---|---|---|---|---|
| 主按钮 | 强调色填充 | 提亮 8% | 压暗 8% | 40% 透明度 + 禁用光标 | 2px 焦点环 |
| 次按钮 | 1px 描边 | 填充浅色 | 压暗 | 同上 | 2px 焦点环 |
| 输入框 | 1px 描边 | 描边加深 | — | 背景置灰 | 描边变强调色 |
| 列表项 | 透明 | 浅色填充 | 压暗 | — | 焦点环 + 描边 |
| 复选框/开关 | — | 描边加深 | 缩放 0.96 | 置灰 | 焦点环 |

**进度条规范**：
- 确定性任务（导出）用**百分比 + 剩余时间**
- 不确定性任务（连接微信的进程查找）用**不确定态动画 + 分步文案**
- 绝不出现"转圈但没有任何文字"的状态

## 七、视觉规范

| 项目 | 取值 |
|---|---|
| 窗口背景 | 跟随系统深浅色（`AppsUseLightTheme` 注册表值） |
| 面板 | 圆角 8px，1px 描边，无投影 |
| 强调色 | 默认品牌暖橙；可选跟随系统强调色（`DWM\AccentColor`） |
| 字体 | 系统 UI 字体（中文 Microsoft YaHei UI） |
| 字号 | 正文 13px / 小字 12px / 标题 15px / 指标数字 24px |
| 间距 | 组件内 8-12px，区块间 16-20px，栏间 0（用 1px 分隔线） |
| 圆角 | 输入 6px，卡片 8px，窗口内嵌面板 12px |

**关于窗口外观**：采用**系统标题栏**。理由不是审美，而是能力——自绘标题栏意味着要自己实现 Snap、系统菜单、Win+方向键与多显示器行为，而系统标题栏免费提供全部四项。

## 八、交互与键盘约定

| 快捷键 | 行为 |
|---|---|
| `Ctrl+O` | 打开 JSON 归档 |
| `Ctrl+E` | 开始导出 |
| `Ctrl+F` | 聚焦搜索框 |
| `F5` | 刷新预览 |
| `Esc` | 关闭对话框 / 取消导出（需确认） |
| `Tab` / `Shift+Tab` | 完整焦点遍历，顺序为左→中→右 |

**其他桌面习惯**：
- 拖放 `.json` 到窗口即导入
- 表格列可排序、可调整宽度
- 右键消息 → 复制内容 / 查看原图 / 复制时间
- 窗口尺寸与位置在关闭时保存，下次恢复（跨显示器失效时回落到主屏）

## 九、实施建议

按"用户可感知收益 ÷ 成本"排序：

| 阶段 | 内容 | 收益 |
|---|---|---|
| **P0** | 统一为一套界面；导出加剩余时间与取消；完成态产物清单 | 直接解决最痛的 3 条 |
| **P1** | 导出预估；媒体缺失提示；连接微信三阶段流程 | 消除误判与惊吓 |
| **P2** | 设置持久化；键盘快捷键；右键菜单；拖放 | 桌面习惯 |
| **P3** | 浅色主题；系统强调色跟随；无障碍焦点环 | 完整度 |

**必须先处理的前置项**：当前工作区存在一套未完成的界面改造（无边框改系统标题栏），且 `dashboard_window.py`、`glass_widgets.py` 两个文件**未纳入版本控制**，任何重构前应先提交或备份，否则改动不可回滚。
